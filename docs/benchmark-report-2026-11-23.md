## 一、结论先行

| rustlings | mo8it | 897 次 / 26.3% | 1,007 次 / 29.6% | 少算 11% |

全部已修，修法见第五节。

其余 10 个问题按严重度列在第五节，都已修复并补了测试。

## 五、发现的问题与修复

### P0-1：同一个人的三个身份被拆成三个人

**现象**：画像数字偏小，且没有任何提示。

**三种形态**（全部实测命中）：

| 形态 | 实例 | 为什么 Git 认不出 |
|---|---|---|
| 同名不同邮箱 | httpie 的 Jakub（.co / .name） | 邮箱不同即不同身份 |
| 重音写法差异 | `Jakub Roztočil` / `Jakub Roztocil` | 字符串不等 |
| GitHub noreply vs 真邮箱 | rustlings 的 `Mo` / `mo8it` | 显示名完全不同 |

**修复**：新增 `identity.find_name_collisions()`，用三条规则识别：
1. 显示名去重音、小写、压空白后完全相同
2. 有任何一方是 `*@users.noreply.github.com`，其登录名与对方的邮箱前缀或名字匹配
3. 每个身份至少有 2 次提交（排除重名路人）

**不给自动合并**，只在报告警告区给出可直接复制的命令：

```
「Jakub Roztocil」在仓库里对应 2 个邮箱（jakub@roztocil.co / jakub@roztocil.name），
看起来是同一个人。合并后才是完整的他：--author "jakub@roztocil.co,jakub@roztocil.name"
```

理由：误合并两个同名真人比漏合并更难纠正，而漏合并用户能看出来（榜单上两行同样的名字）。

---

### P0-2：章节把真实的低谷吞掉了

**现象**：gin 的 2020 年下半年只有 21 次提交（前后半年都在 50+），这段低谷在报告里完全消失，被并进一个 2,093 天的"功能扩张期"。ripgrep 同样：2021-2022 的低迷期被并进一个 2,434 天的章节。

**根因**：判断"两段是否相似"用的是**段内平均值**。

```
seg2  2017-04~2022-04  61 个月  3.94 次/周   ← 内部含 2021 年的塌陷
seg3  2022-05~2023-11  19 个月  3.77 次/周   ← 平稳回升
```

两段平均值只差 4%，判为"相似"并合并。但 seg2 内部从 8 次/周掉到 0.4 次/周 —— 平均值恰好抵消了。

**修复**（三条一起，缺一条都压不住）：
1. 合并时加**跨度上限**：单章不超过总历史的 40%
2. 超过上限一倍且内部无断点的段落，按时间中点强制切开
3. 强制切分有**预算**（章数已够时不切），否则会切出"扩张/打磨/扩张/打磨"的横跳

修复后：

| 仓库 | 修复前 | 修复后 |
|---|---|---|
| gin | 4 章，最长 2,093 天（47%） | 6 章，最长 1,446 天（33%），**沉寂期回来了** |
| ripgrep | 5 章，最长 2,434 天（62%） | 7 章，最长 1,591 天（42%） |
| vite | 4 章，最长 2,089 天（87%） | 6 章，最长 1,094 天（46%） |

### P0-3：空仓库的报错是给开发者看的

**修复前**：

```
✗ git log --numstat --format=%H%P%an%ae%aI%cI%s --no-renames 失败：
  fatal: your current branch 'main' does not have any commits yet
```

**修复后**：

```
⚠ 这个仓库还没有任何提交。`git log` 拿不到历史，先生成一次提交再来。
```

实现：`GitError` 带 `code`（`empty_repo` / `not_a_repo` / `bad_revision`），CLI 按语言翻译，未知错误仍保留原始 stderr（排查时那是唯一线索）。退出码正确：1。

### P1-4：语言构成合计不足 100%

vite 95.6%、httpie 98.1%。原因是榜单只取前 6 名，**剩下的直接丢掉**，没有补 Other。已修：截断后把余量并入 Other 行。修复后 10/10 仓库合计 100.0%（±0.1 舍入）。

### P1-5：只有三天的仓库叫"稳态迭代期"

`_single_chapter` 硬编码 `archetype="steady"`。3 次提交的新仓库也该叫"草创"。已改为按跨度判断：≤180 天 → genesis，否则 steady。

### P1-6：沉寂期被当成"太小的章节"合并掉

`_merge_tiny` 用"跨度 < 3 天"判定小章节。但沉寂期的价值在于**前面那段空档有多长**，不在于自己跨了几天 —— "隔了两年回来提交两次"被并进前一章，最重要的信息就没了。已把 silence / renaissance 排除出该规则。

### P1-7：章节日期缺少年份

侧栏显示 `13-10-23 — 17-09-30`，像 bug（其实是模板故意截取后 8 位省空间）。已改为紧凑年月：`2013-10 → 2017-09`，信息完整且不超宽。

### P1-8：脱敏报告给出无法执行的命令

`--anon` 之后，警告里仍写 `--author "dev-A@redacted,dev-IR@redacted"` —— 邮箱已被打码，照抄必失败。已改为脱敏模式下换用不含命令的文案。

### P2-9：机器人混进"谁在写"

rustlings 的 `allcontributors[bot]` 546 次提交，排第三；fzf 的 `dependabot[bot]` 110 次。报告把它们和真人并列，"贡献者 503 人"也是虚数。

已修：`clean.is_bot()` 识别 `[bot]` 后缀、`*@users.noreply.github.com` 的 bot 段、常见名单（dependabot / renovate / github-actions 等）。榜单只列真人，机器人单独计数：

```
rustlings  authors=501 bots=2 bot_commits=548  榜单: mo8it / liv / fmoko
```

### P2-10：分享卡还写着旧名字

页脚已经改成 gitannals，卡片头部仍是 `GIT CHRONICLE`。已改为读 `TOOL_NAME` 常量。

### P2-11：大仓库仍有 55% 的章节

rustlings 有一章覆盖 2,110 天（55%）。查证后确认：**该段内部确实没有突变**（提交量平稳），强切会造出假阶段。已作为已知限制接受，不变量测试的上限定在 90%（只拦"一章到底"）。

## 六、性能

| 仓库 | 提交 | 分析耗时 | 纯 git 耗时 | 工具开销 |
|---|---:|---:|---:|---:|
| type-fest | 1,621 | 2.3 s | — | — |
| gin | 2,023 | 1.6 s | — | — |
| httpie | 1,797 | 1.7 s | — | — |
| tqdm | 2,132 | 1.7 s | — | — |
| rustlings | 3,406 | 2.2 s | — | — |
| ripgrep | 2,380 | 2.7 s | — | — |
| fzf | 3,776 | 4.0 s | — | — |
| TheAlgorithms | 4,235 | 4.5 s | — | — |
| flask | 5,566 | 4.3 s | — | — |
| vite | 9,951 | **29.2 s** | **25.6 s** | 3.6 s |

合计 36,887 次提交 / 54.2 秒 = **1.47 ms/提交**。

**vite 的 29 秒不是工具的问题**：单独跑 `git log --numstat` 就要 25.6 秒（Windows 上算 diff 慢），工具的额外开销只有 3.6 秒。这一条值得写进 README —— 用户在大仓库上遇到慢，第一反应会怀疑工具。

顺带修了一个性能问题：`filter_noise` 对每个文件路径跑 168 条 glob，vite 上累计 739 万次 `fnmatch`，耗时 13 秒。加了路径缓存后降到 5 秒以内（同一路径只判断一次）。

## 七、已知限制

这些是**测出来的行为**，不是 bug，但用户需要知道：

| 限制 | 说明 | 建议 |
|---|---|---|
| 章节跨度不均 | 最长章可达 55%（rustlings）。匀速仓库切成三段必然是"短-长-短"，长段内部没有突变 | 强切会造假，已选择不切 |
| 活跃标签覆盖率高 | type-fest 15 个文件里 14 个"仍在动" —— 因为它是真的每天都在改 | 可考虑降级为行内小圆点，不占标签位 |
| `(root)` 占位符 | 根目录文件在"主战场"里显示为 `(root)` | 应显示为"根目录" |
| `--author` 模糊匹配偏宽 | `--author liv` 命中 9 人（含 olivia、live.com 邮箱） | 会列候选，但第一次用容易困惑 |
| 脱敏不脱语义 | anon 报告仍写着"6 月大重构、删了 1.6 万行、主战场在 docs" | 定位是"发给不认识你的人" |
| 章节命名可重复 | vite 有四个"功能扩张期"，用年份区分（`· 2021` / `· 2024`） | 已成对出现，可接受 |

## 九、建议的下一步

1. **把身份合并写进 README 的显眼位置**。这是当前最容易踩的坑，而用户不会主动怀疑画像数字。
2. **`(root)` 改成"根目录"**，三行代码的事，但出现在每个报告里。
3. **考虑 `--author` 的匹配收紧**：先精确匹配邮箱，再匹配邮箱前缀，最后才模糊匹配名字，并且在命中多人时直接报错而不是列出 9 个候选。
4. 活跃标签改行内圆点（可选，影响观感不影响正确性）。

不建议现在做的：继续增加图表或指标。10 个真实仓库跑下来，报告的**结构**没有暴露问题，问题都在判定的正确性上，而这一轮已经修完了。
